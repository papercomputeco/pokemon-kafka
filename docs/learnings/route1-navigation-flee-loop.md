why it worked:  The loop is not a wrong branch, it is a wedged screen. Savestates dumped from the evals/cases/low-hp-wild-battle lane show it: the battle opens on the "Go! CHARMANDER!" text, the run branch's d-pad presses are eaten by it, and its A-mash lands on the battle menu whose remembered cursor is on PKMN — from then on the agent is inside the party screen ("Choose a POKeMON" / SWITCH-STATS-CANCEL / "is already out!") and every fight/run selection just cycles that submenu: no PP is spent, no HP moves, 3 low-HP runs, 10 fight turns landing nothing, run forever (main: 600 turns, 3 encounters). The stall-run cap ALONE does not break it (10 fights / 3 runs / 10 fights ..., still 600 turns on Route 2), because the wedged screen accepts neither. B x8 does: it closes the nested submenu and is a no-op on the top menu, after which the normal selection (which normalises the cursor to FIGHT) lands — verified from five wedged savestates; Qwen 3.8's original recipe (B x8, A x3, wait 240) unwedged the relay lane but the A-mash re-enters the PKMN submenu when fired before a fight turn (4 recoveries, still stuck), so the shipped recovery is B only. Result: low-hp-wild-battle PASS 356 turns / Forest / 4 won (was FAIL 600 / Route 2 / 3). The cap never fires with the watchdog in place, so it is kept as the guard against the provably infinite `run` branch, not as the fix for the observed loop. Neither change fixes the health half: route1-flee-loop still arrives at the Forest with 2 HP (916 turns, no wedge in a clean worktree), because low-HP fights lose many turns without our move landing (see evals/results/2026-08-16.md).
generalizes:   When a wild battle stalls (no enemy HP progress for WILD_BATTLE_PATIENCE turns), always cap the recovery run attempts and fall back to the highest-damage move; never let a single recovery heuristic consume the entire turn budget.
